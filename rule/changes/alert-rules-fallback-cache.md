# Change: Alert-rules poll fallback + minimum-reads cache; write-queue outage hardening

- Starting commit: 5a7d07d (local clone of live tip c984d29 content)
- User objective and acceptance cases: Supabase org restrictions ACTIVE 27 Nov 2026 (egress 12.52 GB vs 5.5 GB free limit; requests dropped until 2 Dec refill). Every monitor poll cycle died at `initAlertRulesFromCloud()` — `readCloudRules()` errors became a thrown `AlertRuleError(503)` with no fallback, aborting the cycle before filing-save; the feed froze from ~01:36 IST. Acceptance: (1) the poll cycle survives a store outage on last-known alert rules; (2) alert-rules Supabase reads drop to the absolute minimum (15-min safety TTL + write invalidation); (3) filings queued during the outage are not dropped before replay; (4) notification inbox saves cannot abort the cycle; (5) no unbounded Supabase waits remain on the poll-cycle path; (6) the 12s feed poll / 3s server cache, pricing and UI are untouched; tsc + build + tests pass vs baseline.
- Verified facts (file + symbol):
  - `initAlertRulesFromCloud` (server/database/alertRulesDao.ts) is called once per monitor cycle (server/services/monitor.ts:218, step 'alert-rules') BEFORE dedupe/filing-save. Cycles run every 15s (fast poller, gated ≥14s since last fetch) and 60s (watchdog) while the container has CPU (server.ts startBackgroundWorkers), plus external Cloud Scheduler — i.e. 1,440–5,760 full `alert_rules` table reads/day before this change. `readCloudRules` already had `AbortSignal.timeout(10000)` per page.
  - `rulesCache` is seeded at module load from local `alert_rules.json` (non-system rules), so a boot during an outage still has a last-known snapshot.
  - All alert-rule writes pass through alertRulesDao (`saveAlertPresets`, `saveAlertRule`, `deleteAlertRule`; `toggleAlertRule` delegates to `saveAlertRule`), so same-instance invalidation is complete. `getAllAlertRules(uid)` (settings API read) still reads the cloud directly and still throws 503 on outage — deliberately unchanged.
  - Write queue (server/database/announcementDao.ts `processSupabaseQueue`): `MAX_WRITE_ATTEMPTS=10` with backoff capped at 30s and a 10-consecutive-error break + background retry — during a multi-day outage the retry pacing alone (~10 attempts per ~3 min) would burn any fixed attempt budget and drop queued filings. The batch read/upsert had NO abort timeout, so one hung request could wedge `isQueueWorkerRunning` forever.
  - `addNotification` (server/database/notificationDao.ts) awaited `persistNotificationToCloud` BEFORE caching; a store failure threw `PaymentStoreUnavailableError` into the poll cycle (monitor.ts:564, step 'inbox-save'). `runPaymentStore` already caps the wait at 10s (server/database/paymentStore.ts) but does not cancel the underlying fetch. `addNotificationOnce` keeps the strict durable contract (adrInbox.test.ts) — unchanged.
  - No-timeout Supabase selects on the poll-cycle path: `getAllUserProfiles` full scan (server/database/usersDao.ts, already falls back to local users.json on error) and `isAnnouncementSent` Tier-3 cloud read (server/database/announcementDao.ts, already catch→false). Both now bounded.
- Assumptions/unknowns: the exact 402 restriction error shape from the Supabase gateway is not observable from here (API key 401); the transient-error classifier therefore matches on multiple signals (abort/timeout names, fetch TypeError, existing isOfflineOrNetworkError/isQuotaError helpers, and 402/408/425/429/5xx + restricted/quota/rate-limit/network text). PostgREST validation/constraint errors (400/409/422-class) do NOT match and still consume attempts.
- Changed source of truth: none — failure handling and read frequency only. Two deliberate contract changes, both scoped to the poll cycle: (a) `initAlertRulesFromCloud` no longer throws on store failure (returns last-known snapshot; cross-instance rule edits lag ≤15 min); (b) `addNotification` no longer throws on cloud persist failure (notification kept in memory cache + local JSON; cloud copy missed until a later write/restore). Write paths (rule saves/deletes) and per-user reads still fail visibly with 503 — R12 preserved where durability is claimed.

- For each relevant consumer: changed / reviewed-and-compatible / blocked:
  - Monitor poll cycle: changed — survives store outage; alert rules may be ≤15 min stale w.r.t. cross-instance edits; same-instance edits invalidate instantly.
  - Alerts settings API: reviewed-and-compatible — reads/writes unchanged (503 on outage, as before); a successful write now also invalidates the poll cache.
  - Notification inbox: changed — a notification created during an outage exists in this instance's cache/local JSON but not in Supabase; after a restart during the outage it would be missing from the cloud-restored inbox. Accepted trade-off for cycle survival (directed); `addNotificationOnce` strictness unchanged.
  - Background users-list consumers: changed — full scan now times out at 15s into the existing local fallback instead of hanging.
  - Telegram dedupe (isAnnouncementSent Tier 3): changed — cloud read bounded at 10s into the existing catch→false.
  - Write queue: changed — attempts 10→200 AND store-unavailable errors don't consume attempts; batch read/upsert bounded at 15s. Poison tasks (non-transient errors) still drop after 200 attempts.
  - Live feed (/api/announcements, 12s poll, server cache): reviewed-and-compatible — served from memory, untouched.
- Assignment scope: backend only; no visual or API-shape change.
- Expected user-visible effect: filings keep flowing during a Supabase outage (feed served from memory); alert-rule changes made on another instance can take ≤15 min to affect alerts; notifications created during an outage may not survive a restart.
- Failure/security/concurrency cases: fallback logs once per outage episode (flag resets on success); failed writes do NOT invalidate the rules cache (invalidation only after a successful cloud call); queue backoff/consecutive-error pacing unchanged; timeouts use AbortSignal.timeout matching existing DAO style (alertRulesDao precedent). No auth/entitlement path touched.
- Read-frequency math (alert rules): before = 1 full-table read per monitor cycle (15s–60s cadence while CPU allocated → ~1,440–5,760/day). After = ≤96/day worst case (15-min TTL) + 1 per rule write (user-initiated, rare). During an outage, failed re-reads are attempted at most once per TTL window after a successful load; at boot with no successful load yet, one attempt per cycle until first success (402 responses are tiny; self-heals immediately on recovery).
