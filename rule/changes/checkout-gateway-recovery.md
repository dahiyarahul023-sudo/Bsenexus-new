# Change: Recover checkout after a gateway script failure

- Starting commit: bbb68b9, tested local UX stack.
- User objective: continue release verification and repair a reproducible checkout blocker.
- Verified source: startProPayment sends create-order before the Cashfree SDK is available. loadSdk retains a rejected promise indefinitely. ProCheckoutView clears its busy state on a reported failure but cannot recover that cached rejection.
- Acceptance: SDK outage creates no order, explicit retry loads a fresh script, a successful order keeps the selected plan and the existing same-tab Cashfree redirect, and an obsolete account attempt stops before order creation or handoff.
- Impact: npm run map:impact -- src/utils/cashfree.ts src/components/ProCheckoutView.tsx scripts/verify-checkout-recovery.mjs. Existing server ownership, price, referral attribution, payment verification and entitlement remain authoritative.
- Official integration reference: https://www.cashfree.com/docs/payments/online/web/redirect
- Checkout action: the chosen plan and reviewed referral state are captured by the Pay button. A single attempt owns the busy state. SDK loading shares an in-flight script, expires after 12 seconds and clears the failed script and promise. The order POST occurs only after SDK readiness. Account, selected checkout entry, closure or unmount abort an obsolete attempt; abort after submission does not imply a server ledger rollback.
- Consumers: ProCheckoutView and the SDK launch helper changed. Pricing, plan and referral inputs, the authenticated order API, durable pending ledger, Cashfree return and recovery, billing/receipts, verified entitlement, and delivery are compatible with the existing contract. A reported SDK error restores the controls without replaying the order. The same-tab redirect remains the handoff, and server confirmation still owns paid status.
- Actual browser evidence: Playwright fixture reproduced one order created on an SDK failure before the change. After the fix, a blocked script and a simulated timeout each create zero orders, a manual retry loads a fresh script and uses the chosen monthly plan, the synthetic sandbox-mode SDK gets the existing same-tab target, an SDK error frees the button without replay, and switching accounts during download suppresses the old attempt. The test intercepts the gateway script and order API and sends no real provider traffic.
- Additional release evidence: a separate signed-in fixture confirmed an in-flight note save remains isolated across account switch and is visible again to its owner. All 1,003 application tests passed, including the 42 focused payment, auth, notes, inbox transport, Telegram delivery and referral cases. Production build, startup budget, typecheck, map and dev-runtime Chromium checks passed.
- Release boundary: this is a local source fix. No Cashfree provider sandbox, payment, Telegram delivery, live account mutation, production deploy or schema change. Roll back by reverting this commit.
